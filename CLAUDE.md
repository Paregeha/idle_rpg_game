## Проєкт

Мобільна idle RPG на Flutter з онлайн-складовою: лідерборди, гільдії, спільний бос.
Ключова властивість жанру: **прогрес — це чиста функція від стану й часу**, тому сервер
може перерахувати будь-який прогрес самостійно, без потоку подій від клієнта.

## Структура монорепо

```
/packages/game_core     # чистий Dart, БЕЗ Flutter. Формули, simulate(), баланс, BigNum
/apps/client            # Flutter-застосунок
/apps/server            # Serverpod
/apps/server_client     # згенерований Serverpod-клієнт (не редагувати руками)
/tools/balance          # CLI-скрипти симуляції балансу
```

Керується через `melos`. Команди: `melos bootstrap`, `melos run test`, `melos run analyze`.

## Залізні правила

1. **`game_core` не залежить від Flutter.** Жодних `import 'package:flutter/...'`.
   Перевіряється в CI. Цей пакет підключений і в клієнт, і в сервер — це єдина правда про правила гри.
2. **Сервер — джерело правди.** Клієнт симулює локально лише для плавності UI.
   При розходженні виграє сервер. Не додавай ендпоінтів, де клієнт надсилає результат
   замість наміру (`POST /addGold` — заборонено, `POST /buyUpgrade {id}` — правильно).
3. **Ніякого `DateTime.now()` у логіці гри.** Тільки інжектований `Clock`.
   Час у стані — завжди UTC-мілісекунди від сервера, не з пристрою.
4. **Числа гри — `BigNum`, не `double`.** Idle-числа виходять за межі `double` за години гри.
5. **Детермінізм.** Будь-який RNG — тільки seeded, seed зберігається у стані.
   `simulate(state, dt)` з тим самим входом завжди дає той самий вихід.
6. **Баланс — у даних, не в коді.** JSON/YAML у `game_core/assets/balance/`, версіонований.
7. Flame використовується **тільки** для бойової сцени (`GameWidget`). Меню, інвентар,
   гільдія — звичайний Flutter UI. Не переписуй UI на компоненти Flame.

## Цикл роботи над задачею

Для кожної задачі з `TASKS.md` дотримуйся послідовності:

1. **План.** Прочитай задачу, назви файли, які створиш/зміниш, і чекай підтвердження.
   Не пиши код одразу.
2. **Тести.** Спочатку тести з Acceptance-критеріїв задачі. Вони мають упасти.
3. **Реалізація.** Мінімальний код, щоб тести пройшли.
4. **Перевірка.** `melos run analyze && melos run test`. Червоне — не рухаємось далі.
5. **Коміт.** Conventional Commits: `feat(core): offline progress simulation`.
   Гілка `feat/T-042-offline-progress`.
6. **Закриття.** Постав `[x]` у `TASKS.md` і, якщо з'явилось архітектурне рішення,
   додай рядок у `docs/decisions.md`.

## Стиль коду

- `dart format`, `flutter_lints` + `very_good_analysis`.
- Іменування, коментарі, документація — англійською. Тексти для гравця — через локалізацію (`uk`, `en`).
- Immutable-моделі через `freezed`. Стан гри ніколи не мутується на місці.
- Публічні API `game_core` мають dartdoc з формулою, якщо метод рахує щось балансне.

## Чого не робити

- Не додавати залежність у `game_core` без явного дозволу.
- Не змінювати згенеровані файли (`*.g.dart`, `*.freezed.dart`, `apps/server_client`).
- Не чіпати міграції БД заднім числом — тільки нова міграція вперед.
- Не хардкодити числа балансу в логіці.
